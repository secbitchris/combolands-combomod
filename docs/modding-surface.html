The safety boundary is one question

Does the change write a value into a save file that an unmodded client cannot resolve? Everything else is noise.

Combolands writes two save files, both JsonUtility JSON, gzipped and base64-encoded. The decisive detail is that the run save stores per-piece deltas only — LocalRangeChanges, LocalMultChanges, Count, StoredValue. No base stat is serialized anywhere. Base values are re-read from code on every load, which is why rebalancing is invisible to the save format in both directions.

Three tiers of change

Tier 1 · free

Cannot touch a save

Reversible by deleting the mod. A save written while it was loaded opens fine in an unmodded client.

  • Rebalancing any existing building or item — every knob in the table below
  • Rewriting behaviour logic for existing tags
  • All text, sprites, audio, VFX, UI
  • Draft-pool composition and weights among existing tags
  • Map size and tile layout (Width/Height serialize as plain integers)
  • The three declared-but-unused enum members

Two facts underwrite this. There is zero AssetDatabase / SetDirty / SaveAssets in the build, so runtime ScriptableObject edits physically cannot reach disk. And balance lives in code, not data — behaviour constructors call SetRarity, SetBehaviourCooldownParam and friends.

Tier 2 · guard it

Writes plain integers

  • Modifying the serialized deltas themselves. These carry no identity meaning, so vanilla reads them fine — a building left with +5 range is a balance oddity, not corruption.
  • Winning a run with mods active. This records victories in Unlocks.save and fires EvaluateAchievements().

The guard is one line: AchievementsHandler.achievementPlatform is a public field of type IAchievementPlatform. Assign a no-op implementation and Steam sees nothing. The handler enables itself in Start(), so the swap has to happen after that.

Tier 3 · needs a framework

Mints new enum values

JsonUtility writes enums as bare integers. A modded (GameTag)1001 serializes as 1001, and a vanilla load resolves it to a tag with no data behind it.

  • New buildings, items, consumables, heirlooms, gems, tomes
  • New GamePieceCategory, TargetCategory, TileType, ThemeType, CouncilCharacter, GameMechanicUnlock, ProgressionRank

Doing this properly needs a stable tag allocator, postfixes on roughly 13 Enum.GetValues(typeof(GameTag)) call sites, sidecar save manifests, and a load-failure guard around IOManager.LoadFile — which currently has no try/catch at all.

What actually constrains you

Every setter is a bare field assignment — there is no validation anywhere. The real constraints are downstream, and there are remarkably few.

Range has no numeric ceiling but a practical one: BuildingController maintains a precomputed tile-to-buildings index, so cost is paid on rebuild rather than per query. On a board this size, range 8 already reaches most tiles, so anything past ~12 is gameplay-meaningless before it is ever a performance problem.

Never set a draft weight to exactly zero

ChooseBag.RemoveElement only removes entries whose weight is greater than 0. An entry at exactly 0 can still be chosen but never removed, so GetRoll picks it repeatedly — and because results collect into a HashSet, the caller silently receives fewer draft options than it asked for. Use a small epsilon instead; it keeps the entry removable while making it effectively unreachable.

Shop composition

Relative weights into a normalized bag: Heirloom 20, Favour 6, Blueprint 4, BuildingSupply 4, Spell 2. Blueprint price is a flat 4 regardless of building or milestone. Sell price is floor(buy / 2).

So (GameTag)1001+ is an unclaimed range that already routes as a building — as close to a sanctioned extension point as the codebase offers. The catch is that 13 call sites enumerate via Enum.GetValues, which returns declared members only, so a custom tag is correctly classified and simultaneously invisible.

The trap that wastes an hour

Range, multiplier, and cooldown are cached per piece behind sentinel values (-9999, -9998f). Change a base stat at runtime and buildings already on the map keep serving stale numbers.

The fix is public: BuildingExtensions.ResetCaches() walks every placed building and clears its cache, and guards internally on whether a controller exists, so it is safe to call from the main menu. 

ComboModApi.InvalidateStatCaches();   // wraps BuildingExtensions.ResetCaches()

Without it a rebalance appears to work on newly placed buildings and silently no-ops on everything already standing — the two states look identical from inside the game.

What the environment takes off the table

Checked for, and absent: no anti-tamper, no checksums, no integrity verification. No leaderboards, no telemetry, no analytics, no network calls beyond Application.OpenURL to the Steam page, Discord, and the developer's site. Fully offline single-player.

There is also no RNG seeding anywhere — no Random.InitState, no seeded runs. Nothing to desync, and no reproducibility contract to break.

So there is no ban risk, no shared scoreboard to pollute, and no external state to corrupt. The only thing a mod can damage is your own two save files.

Verified against the running game

ComboMod implements the Tier 1 surface and was confirmed live: version gate matched, tunes applied exactly once each, real before/after values logged. When the game patched from 24930533 to 24951781 mid-session the gate caught it immediately — and re-auditing the new binary found every knob, value, and reflected field unchanged.
